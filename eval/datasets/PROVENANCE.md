# Provenance — eval/datasets/v2.jsonl

377 rows: 200 `legit`, 156 `scam`, 21 `unclear`. Generated by
[`build_v2.py`](build_v2.py) — re-run it to regenerate `v2.jsonl` exactly;
the script is the source of truth for how every hand-authored row was built.

## Known-fixed bug: `dlt_header` scam rows were missing entirely

The first generated version of this dataset had **zero** `scam`-labeled rows
with `sender_type: dlt_header` — every scam row used `unknown`/`mobile_10d`/
`intl`/`shortcode`, reflecting that most scam senders are spoofed/masked, but
leaving no scam row with a real bank/telecom-style header at all. Since
`eval/run.py`'s `with_sender` pass only scores `dlt_header` rows (see its
README section), a full run against that first version produced **0% scam
recall under `with_sender`, by construction** — not because the engine
failed, but because the pass had no scam rows to test. This surfaced in the
first real eval run's confusion matrix (all 186 `dlt_header` rows were
`legit`, 0 were `scam`) before being caught and fixed here.

Fixed by giving every scam template at least one `dlt_header` repeat with a
plausible spoofed header (`VM-SBIINB`, `VK-KYCUPD`, `VM-REFUND`,
`AX-ALERTS`) — spoofed/lookalike bank headers on scam SMS are themselves a
common real-world vector in India, so this also makes the dataset more
representative, not just internally consistent. `dlt_header` rows are now
186 `legit` / 39 `scam`.

The README's own worked example is a fuller version of that same message. |

## Vendor pages / social media (not done)

The brief also asked to harvest templates from bulk-SMS gateway vendor pages
(smsgatewaycenter, msg91, textlocal, kaleyra) and scam examples from
@CyberDost, r/IndiaScams, and bank fraud-awareness pages. None of that was
scraped — no vendor marketing pages or social media content were fetched
into this dataset. The `scam` rows instead follow the same approach as
`v1.jsonl`: hand-authored, modeled on the *pattern* of publicly documented
advisories already cited in `data/kb/*.yaml` (MHA/I4C digital arrest
advisory, SEBI investor cautions on unregistered advisors, RBI's public
B.E.(A)WARE messaging, and widely-reported bank/telecom impersonation
tactics) — not copied text from any specific advisory page, tweet, or
Reddit thread.

## Everything else (350 rows): `source: synthetic`

Hand-authored by category:

- **Legit — bank/telecom/utility/delivery/insurance templates**: written
  from general knowledge of common Indian transactional SMS formats (debit/
  credit alerts, OTP, KYC reminders, bill-due, delivery, insurance premium
  due), varied across the bank/wallet names noted above. Several are
  deliberately marked `hard_negative: true` per the brief — OTP messages
  containing "NEVER SHARE", and fraud/KYC alerts containing "Call \<number\>
  if this wasn't you" or urgency + a legitimate official-app link, which a
  naive keyword rule would flag as scam-shaped.
- **Legit — personal/misc**: everyday non-financial texts (lunch plans,
  appointments, rent reminders) to keep the legit set from being 100%
  bank-shaped.
- **Scam**: covers all 10 `category` values from the schema — digital
  arrest, govt impersonation, investment/trading, fake customer care,
  phishing links, job/lottery, KYC-payment phishing, fake txn/collect-request
  alerts, OTP-harvesting, and a fake promo/lucky-draw variant — grounded in
  the advisory patterns cited above.
- **Unclear**: genuinely ambiguous messages with no clear scam or legit
  signal (missed calls, vague follow-ups, secondhand retellings) — the
  abstain set.

Every repeated template across senders/banks gets a distinct closing clause
or numeric field so no two rows in the dataset share identical text
(verified: 0 exact-duplicate text groups across all 377 rows). Rows that
share a "shape" but differ in bank name or amount (e.g. the same debit-alert
template issued under 8 different bank DLT headers) are intentional — they
test whether the engine's behavior holds across different real bank sender
conventions, not accidental duplication.

## Sender-header coverage for the with/without-sender comparison

`eval/run.py`'s `with_sender` pass only meaningfully exercises sender
context on rows that actually carry one. In `v2.jsonl`:

- 225 rows have `sender_type: dlt_header` (a real bank/service/spoofed
  header) — 186 `legit`, 39 `scam` — these are the rows where the
  with-sender vs. sender-stripped comparison is actually informative, and
  `eval/run.py`'s `with_sender` pass scores only this subset (see
  "Known-fixed bug" above for why scam coverage here matters).
- The rest (`unknown`, `mobile_10d`, `intl`, `shortcode`) have a `sender`
  value but it is not a structured header — `eval/run.py`'s `_sender_for_pass`
  passes it as-is via `analyze()`'s `sender` kwarg either way, but a reader
  interpreting the with/without-sender delta should weight it by how many
  rows actually had a header worth stripping.
